# ADR 0006: Provider-Tracked Object Catalog

- Status: Accepted for Version 2.3 development; amended for Versions 2.3.1 and 2.3.2
- Date: 2026-08-30
- Last amended: 2026-09-01
- Maturity: Experimental
- Safety class: non-operational

## Context

The preferred GP/OMM catalog contains objects for which the configured provider publishes current SGP4 element sets. It is not a complete inventory of the provider's tracked objects. In particular, many debris fragments, rocket bodies, and unknown objects appear in SATCAT without a current public element set. Radar cross-section can be very small or absent and is not a physical-diameter measurement.

## Decision

Version 2.3 maintains two related but separate populations:

1. The GP/OMM catalog remains the only source of propagated positions.
2. A derived, chunked tracked-object catalog represents every accepted record in the configured bundled SATCAT snapshot, preserves full catalog identifiers and provider metadata, and joins GP/OMM records by canonical NORAD identity.

Tracked records retain independent object type, orbit class, catalog membership, lifecycle, propagation availability, and provenance fields. A record without validated current GP/OMM elements is metadata-only. It remains searchable and inspectable but never receives a synthetic element set, scene marker, orbit, footprint, ground track, or conjunction-screening state.

The catalog manifest is the atomic publication pointer. It identifies content-addressed chunks, their hashes and counts, the source revisions, current and history-scope population counts, quarantines, and coverage invariants. The authoritative population partition is `total == current + history_total`; decay-dated `historical` and complete-reconciliation `absent` are potentially overlapping diagnostics inside `history_total`, not additive partitions. Availability separately satisfies `total == propagatable + metadata_only` and `current == current_propagatable + current_metadata_only`. Chunks are validated before manifest promotion. Failed or incomplete builds preserve the last-known-good manifest, and unchanged source revisions do not rewrite catalog bytes.

The browser loads the manifest and required chunks only after the GP-priority default MEO view is interactive. Orbit filters, object-type filters, lifecycle scope, and tags are independent dimensions. `ALL` means all records in the selected current/historical scope, while the globe and Mercator map contain only finite, current-epoch propagatable positions. Counts distinguish tracked, filtered, propagatable, metadata-only, render-ready, historical, and quarantined records.

## Scientific Boundary

"All tracked" means all accepted records published in the configured SATCAT snapshot. It does not mean every physical debris particle, every object known to any provider, or every tracked object has public current orbital elements. The implementation does not infer physical size from radar cross-section and does not crawl per-object GP endpoints to simulate bulk coverage.

## Operations

The opt-in server scheduler rebuilds the tracked catalog from the same daily SATCAT snapshot and current GP/OMM last-known-good data. Existing conditional-request, complete-source reconciliation, shrink protection, atomic promotion, bounded backup, error redaction, and graceful-stop controls continue to apply. The tracked revision participates in data-update status and browser revision refresh.

Static deployments package the manifest and only its referenced chunks. They do not execute the scheduler. Publishing a newly generated provider snapshot requires a separate byte-specific redistribution and release review.

## Version 2.3.1 Amendment

Version 2.3.1 leaves tracked `schema_version: 2.3.0`, chunk records, manifest descriptors, and manifest/chunk APIs unchanged. Only the exact orbit `ALL` plus object type `DEBRIS` workflow activates additional browser facets derived from existing fields: position availability, reported RCS bands including not reported or invalid, owner/country, launch-year range, launch site, provider status, and international designator/tag. These facets intersect within that special all-debris workflow and round-trip with it in shared state; ordinary orbit/object-type/history/tag filtering remains independent outside the panel. No admitted field supports authoritative mass or weight, so the application provides no mass/weight filter and never infers either value, diameter, or physical size from RCS.

Generic browser copy uses tracked-object terminology. Counts explicitly distinguish matched, positioned, and metadata-only records. The rendering color key maps payload to cyan, debris to red, rocket body to amber, mission-related to green, unknown to gray, and selected to white. The Globe point layer remains color-only, without per-type shapes or rings. For 0 through 499 render-ready/drawn objects, its detailed path samples only the alpha silhouette of the bundled same-origin `icons/ob_satellite.png`, renders it at a fixed 16 screen pixels with `sizeAttenuation: false`, and applies the exact canonical vertex color. At 500 it removes the map, restores perspective attenuation, and switches to density size `0.025`; the procedural white-alpha circle exists only as a load-failure fallback. Detailed Mercator may add type glyphs and selection rings through 1,000 drawable objects; dense Mercator above 1,000 is color-only. Red means only an authoritative `object_type=DEBRIS`; it never represents hazard, collision risk, proximity, physical size, mass, or RCS magnitude. Color cannot override the propagation boundary: a red debris marker exists only when the record has an exact validated current GP/OMM join and a finite propagated state.

The GP acquisition scope expands from `active` to `active` plus `fengyun-1c-debris`, `iridium-33-debris`, and `cosmos-2251-debris`. The three event collections are a partial positioned-debris subset, not complete debris or provider-universe coverage. Incremental updates merge the newest validated element epoch per canonical NORAD identity. Reconciliation may replace only after all four responses succeed, validate, and contain no quarantines. Metadata records desired `source_groups`, accepted-byte `catalog_source_groups`, `source_scope_verified`, structured partial-scope semantics, and `provider_completeness_claim: false`; tracked provenance uses actual catalog groups.

Scope migration is fail-closed. Metadata inherited from the prior active-only acquisition is unverified for the expanded scope, so its conditional validators cannot establish four-group coverage. Requests remain unconditional and due until one complete successful four-group cycle sets `source_scope_verified: true`; `304`-only responses, a failed group, a partial response, or any quarantine preserve last-known-good data and revisions and remain validator-free on retry. The live attempt at `2026-08-30T20:33:29Z` returned HTTP 503, recorded the configured scope as unverified, retained actual `catalog_source_groups: [active]`, and promoted no GP response. A later tracked build corrected provenance metadata without changing its catalog revision, chunks, counts, or position coverage.

Consequently, the frozen snapshot still has 12,490 current and 23,348 historical debris records, all metadata-only with `NO_CURRENT_ELEMENTS`, and zero real positioned debris. This is a data-availability result, not a rendering defect. Deterministic fixtures can exercise the red rendering contract, while the real scene remains empty of debris until a later fully accepted GP refresh supplies exact current elements. Repository owner `arcazj` approved one publication of the exact final post-recording Version 2.3.1 provider/tracked/static/validation/source bytes through `origin/master` and repository-root GitHub Pages. Every later generated, refreshed, or changed byte returns to the separate exact-byte publication gate; the approval is not a completeness, scientific-validation, candidate, or operational claim.

The optional Python server treats the manifest, metadata, all referenced chunks, matching pointer revisions, raw GP/SATCAT bytes and their metadata hashes, and current GP/SATCAT source revisions/groups as one read boundary. Tracked API routes and equivalent server-static aliases return no tracked bytes unless that entire publication is coherent, and they respond with the exact manifest/metadata snapshot that passed validation rather than reopening it after the check. Incoherence produces a bounded `503 TRACKED_CATALOG_UNAVAILABLE` problem response, degrades health, and leaves the client on its GP-only fallback; unsafe or unreferenced chunk names remain `404`. Plain static hosting cannot enforce this per request and therefore depends on the curated builder rejecting an incoherent frozen closure before publication.

## Version 2.3.2 Amendment

Version 2.3.2 leaves tracked `schema_version: 2.3.0`, chunk records, manifest descriptors, manifest/chunk APIs, and the GP-only position boundary unchanged. The Version 2.3.1 debris facets activate whenever `DEBRIS` is the sole selected object type and the orbit selection is nonempty, rather than only under exact orbit `ALL`. Orbit, object-type, history, tag, and facet dimensions remain independent and share-state restorable. No mass, weight, diameter, or risk value is inferred.

The browser keeps matched, positioned, and position-unavailable coverage visible with scope, catalog state, and an available generation timestamp. A virtualized, sortable results surface exposes all matches, on-map records, and position-unavailable records with keyboard navigation, focus restoration, and narrow-viewport behavior. A positioned record may be selected directly from either Globe or Mercator, but direct picking uses the existing canonical selection and eligibility path; a miss leaves selection unchanged and a metadata-only record remains unpickable on the map and details-only elsewhere.

The revisioned scheduled-update data plane is a separate operational-integrity decision documented in ADR 0007. It validates isolated private candidates before an atomic runtime-pointer promotion and does not alter this catalog's public schema, provider-completeness disclaimer, scientific claims, or static publication contract. Version 2.3.2 remains Experimental and non-operational. Repository owner `arcazj` approved one exact final post-recording source publication to `origin/master`; this does not approve either private candidate, a manual Pages artifact, or later changed bytes. Its local aggregate, fixed-point static, rollback, local-attestation, and 334-artifact/17-executable/94-evidence validation inventory are recorded. Remote Pages deployment/attestation, required-reviewer/self-review environment settings, clean committed-tree binding, named profiles, and independent review remain pending.

## Consequences

- Small and missing-RCS debris remains included instead of being silently filtered.
- Metadata-only records can be found without creating scientifically false positions.
- Selected-object screening metadata, the visible catalog summary, and exports report the current tracked population, propagatable population, metadata-only population excluded for lack of current elements, and their input-coverage fraction. This is not pair-screening completeness or collision probability.
- Large catalogs require lazy loading, bounded search results, independent count diagnostics, and scale tests.
- Disabling `experimental_tracked_object_catalog` restores the Version 2.2 GP-only browser path without deleting evidence.
- A one-sided pointer, corrupt closure, or stale GP/SATCAT lineage cannot be exposed as a partial tracked catalog through the optional server.
