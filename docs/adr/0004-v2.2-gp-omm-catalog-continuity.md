# ADR 0004: GP/OMM Catalog Continuity in v2.2

- Status: Accepted for Version 2.2 development
- Date: 2026-08-22
- Decision owners: project maintainers

## Context

The legacy runtime catalog is serialized as TLE and therefore cannot represent newly assigned NORAD catalog identifiers above the five-digit TLE field. A successful TLE refresh can consequently omit valid post-2026-07-11 objects while appearing technically successful. Launch and confirmed-decay timelines also derived availability from propagatable records or retained module-level caches, allowing a missing orbit or an old browser dataset to hide a valid lifecycle event.

Version 2.1 already introduced bounded CCSDS OMM adapters and common propagation contracts for the durable screening service, but it did not admit or package a live OMM-capable GP feed for the browser catalog.

## Decision

Version 2.2 is a development-only catalog-continuity milestone. The application will:

1. Treat CelesTrak GP OMM JSON as the preferred current orbital-element feed and preserve complete NORAD identifiers as strings.
2. Store canonical OMM fields under `element_set.omm`; it will not synthesize TLE lines, truncate identifiers, or use Alpha-5 to disguise six-digit identities.
3. Normalize only the documented omitted OMM constants required by the supported CelesTrak profile: Earth, TEME, UTC, SGP4, and OMM 2.0. Unsupported frames, theories, invalid epochs, non-finite fields, and ambiguous identities are quarantined per record.
4. Initialize OMM with satellite.js `json2satrec` and legacy TLE with `twoline2satrec`, deduplicating by normalized NORAD ID and newest valid element epoch.
5. Publish GP as `json/gp/GP.json` and `/api/gp`, with its exact generated sidecar available at `/api/gp-metadata`; the generic `/api/satellites` route returns preferred GP with legacy TLE fallback. `json/tle/TLE.json`, `/api/tle`, and `export-tle` remain deprecated compatibility paths for one development release and must not contain synthetic OMM-as-TLE data.
6. Re-derive orbit class from finite numeric mean-element metrics for both outputs. During the one-release compatibility window, enrich GP display group/tags only through an exact full-string NORAD join to the first meaningful compatibility TLE tag, preserving a prior meaningful GP tag when unmatched. Bind the compatibility source revision, deterministic tag-map revision, and match counts in GP metadata. This never supplies orbital state or weakens six-digit identity.
7. Make one CelesTrak `active` request for preferred GP and one for default incremental TLE compatibility maintenance; remove the overlapping/failing incremental `last-30-days` request. Retain the historical compatibility multi-group list only behind explicit `export-tle --all`.
8. Build a separate SATCAT-backed launch-event catalog. A valid lifecycle event does not depend on a propagatable orbit; unmatched launch records are details-only and cannot trigger orbit propagation.
9. Keep confirmed decay data separate from orbital elements, evaluate GP/launch/decay due work independently, and allow launch and decay updates to run in the same scheduler cycle.
10. Publish a deterministic composite `data_revision` over GP, launch, and decay revisions for cache invalidation, while retaining GP-only `catalog_revision` compatibility and exposing each component separately.
11. Preserve atomic writes, backups, conditional requests, freshness guards, dry runs, provenance, quarantine counts, and last-known-good artifacts. HTTP errors and malformed or partial replacement data cannot be reported as successful completion. When GP metadata is absent, data health reports TLE fallback only if the packaged TLE file is larger than the empty `[]` sentinel; this is artifact availability, not validation, and otherwise the state is unavailable.

## Consequences

- Six-digit and larger NORAD identifiers can remain lossless through ingestion, API, browser identity, timeline, and propagation contracts.
- Consumers must understand mixed TLE/OMM records or report an explicit tested limitation; silently dropping OMM records is prohibited.
- Launch and decay freshness becomes independently observable through packaged event catalogs and `/api/data-update-status`; either component can advance the browser refresh token without a GP change.
- Static artifacts must package GP, launch, decay, metadata, and every required OMM runtime dependency. Without an explicit API base, static pages poll those same-origin metadata sidecars and can reload operator-replaced packaged data in the current document, but they never fetch providers or mutate the deployment; an unchanged immutable artifact cannot become newer. Explicit API configuration selects the separate server path, not direct provider ingestion.
- Existing TLE integrations receive a deprecation window, but TLE coverage after the five-digit boundary remains inherently incomplete.
- Compatibility tags remain a temporary display/filter enrichment with explicit revision provenance; they do not make TLE the orbital source or establish operator identity.

## Scope Boundary

This decision does not add collision probability, CDM/covariance analysis, risk scoring, alerts, reports, or maneuver recommendations. Version 2.2 remains Experimental, non-operational, and in development publication state. Provider access and local evaluation do not establish redistribution approval, authoritative completeness, or operational suitability.

ADR 0005 records the separately bounded Version 2.2 browser filtering, details, layering, clock, visual interpolation, and ephemeris-range follow-up. It does not change this data-source decision or its governance gates.

## Rollback

Rollback is documented in `docs/engineering/ROLLBACK_V2_2.md`. The safe fallback restores the last-known-good 2.2 GP/event artifacts or a previously archived 2.1 artifact. Falling back to legacy TLE is a visible reduced-coverage mode and must never be presented as current complete catalog coverage.
