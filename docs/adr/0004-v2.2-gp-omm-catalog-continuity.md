# ADR 0004: GP/OMM Catalog Continuity in v2.2

- Status: Accepted for Version 2.2 development
- Date: 2026-08-22
- Daily-maintenance amendment: 2026-08-29
- Full-replacement safety amendment: 2026-08-29
- Decision owners: project maintainers

## Context

The legacy runtime catalog is serialized as TLE. Its five-character field can encode a limited Alpha-5 subset, but it cannot provide complete current six-digit catalog coverage. A successful TLE refresh can consequently omit valid post-2026-07-11 objects while appearing technically successful. Launch and confirmed-decay timelines also derived availability from propagatable records or retained module-level caches, allowing a missing orbit or an old browser dataset to hide a valid lifecycle event.

Version 2.1 already introduced bounded CCSDS OMM adapters and common propagation contracts for the durable screening service, but it did not admit or package a live OMM-capable GP feed for the browser catalog.

## Decision

Version 2.2 is a development-only catalog-continuity milestone. The application will:

1. Treat CelesTrak GP OMM JSON as the preferred current orbital-element feed and preserve complete NORAD identifiers as strings.
2. Store canonical OMM fields under `element_set.omm`; it will not synthesize TLE lines, truncate identifiers, or use Alpha-5 to disguise six-digit identities.
3. Normalize only the documented omitted OMM constants required by the supported CelesTrak profile: Earth, TEME, UTC, SGP4, and OMM 2.0. Unsupported frames, theories, invalid epochs, non-finite fields, and ambiguous identities are quarantined per record.
4. Initialize OMM with satellite.js `json2satrec` and legacy TLE with `twoline2satrec`, deduplicating by normalized NORAD ID and newest valid element epoch.
5. Publish GP as `json/gp/GP.json` and `/api/gp`, with its exact generated sidecar available at `/api/gp-metadata`; the generic `/api/satellites` route returns preferred GP with legacy TLE fallback. `json/tle/TLE.json`, `/api/tle`, and `export-tle` remain deprecated compatibility paths for one development release and must not contain synthetic OMM-as-TLE data.
6. Re-derive orbit class from finite numeric mean-element metrics for both outputs. During the one-release compatibility window, enrich GP display group/tags only through an exact full-string NORAD join to the first meaningful compatibility TLE tag, preserving a prior meaningful GP tag when unmatched. Bind the compatibility source revision, deterministic tag-map revision, and match counts in GP metadata. This never supplies orbital state or weakens six-digit identity.
7. Make one CelesTrak `active` request for preferred GP and one for default incremental TLE compatibility maintenance; remove the overlapping/failing incremental `last-30-days` request. Retain the historical compatibility multi-group list only behind explicit `export-tle --all`. Decode valid numeric and Alpha-5 TLE catalog fields to canonical full strings without claiming complete six-digit coverage.
8. Build a separate SATCAT-backed launch-event catalog. A valid lifecycle event does not depend on a propagatable orbit; unmatched launch records are details-only and cannot trigger orbit propagation.
9. Keep confirmed decay data separate from orbital elements. When server maintenance is explicitly enabled, evaluate GP, compatibility TLE, SATCAT, launch, decay, and reconciliation due state independently while sharing one lock and at most one SATCAT fetch per cycle. Start catch-up only after the HTTP bind and continue until orderly shutdown.
10. Run normal maintenance as non-pruning incremental `PARTIAL` upserts. Only a structurally valid complete `active` GP/TLE reconciliation may remove objects and record `COMPLETE`; preserve launch and confirmed-decay history when a later SATCAT snapshot omits an older event.
11. Publish a deterministic server `data_revision` over GP, compatibility TLE, SATCAT, launch, and decay revisions for cache invalidation, while retaining GP-only `catalog_revision` compatibility and exposing each component separately. Static deployments continue to compute a packaged-file revision token because they have no scheduler.
12. Preserve atomic writes, conditional requests, freshness guards, dry runs, provenance, quarantine counts, content-aware no-op data writes, and last-known-good artifacts. Changed data promotions create collision-safe timestamped backups and retain the newest seven per artifact. An accepted conditional `304` records successful revalidation and resets the applicable daily due age without changing data bytes/revisions or creating a backup. HTTP errors and malformed, partial, or unproven-complete replacement data cannot be reported as successful reconciliation. When GP metadata is absent, data health reports TLE fallback only if the packaged TLE file is larger than the empty `[]` sentinel; this is artifact availability, not validation, and otherwise the state is unavailable.
13. Protect every reconciliation/full replacement, including SATCAT, when the established prior catalog contains at least 1,000 records. Both candidate size and canonical NORAD overlap must retain at least 75% of the prior catalog. `--force` changes freshness eligibility only. An explicit `--allow-large-catalog-shrink` recovery override is confined to direct `export-gp`, `export-tle`, and `refresh-satcat` commands; scheduled `maybe-update` and server operation never expose or pass it.
14. Keep provider access default-off. The daily profile exposes independent interval flags, per-dataset status/errors, bounded jittered retry, stale-lock recovery, and graceful worker shutdown. GP, TLE, SATCAT, launch, and decay metadata persist their latest errors so status can reconstruct history after restart. The public status projection recursively bounds and credential-redacts nested result errors. Static hosting, including GitHub Pages, cannot run the scheduler.

## Consequences

- Six-digit and larger NORAD identifiers can remain lossless through ingestion, API, browser identity, timeline, and propagation contracts.
- Consumers must understand mixed TLE/OMM records or report an explicit tested limitation; silently dropping OMM records is prohibited.
- GP, compatibility TLE, SATCAT, launch, decay, and reconciliation state becomes independently observable through metadata and `/api/data-update-status`; a successful component promotion can advance the connected-browser refresh token without a GP change.
- A suspiciously small or identity-unrelated production-scale provider response fails closed and preserves the prior bytes. Deliberately accepting such a replacement requires a direct, explicit operator override that is unavailable to unattended maintenance.
- Static artifacts must package GP, launch, decay, metadata, and every required OMM runtime dependency. Without an explicit API base, static pages poll those same-origin metadata sidecars and can reload operator-replaced packaged data in the current document, but they never fetch providers or mutate the deployment; an unchanged immutable artifact cannot become newer. Explicit API configuration selects the separate server path, not direct provider ingestion.
- Existing TLE integrations receive a deprecation window. Explicit Alpha-5 identifiers round-trip through canonical full-string identity, but TLE coverage beyond the numeric five-digit range remains inherently incomplete.
- Compatibility tags remain a temporary display/filter enrichment with explicit revision provenance; they do not make TLE the orbital source or establish operator identity.

## Scope Boundary

This decision does not add collision probability, CDM/covariance analysis, risk scoring, alerts, reports, or maneuver recommendations. Version 2.2 remains Experimental, non-operational, and in development publication state. Provider access and local evaluation do not establish redistribution approval, authoritative completeness, or operational suitability. A separate repository-owner confirmation dated 2026-08-29 records data-owner redistribution approval only for the exact Version 2.2.1 bundled-source snapshot and repository-root GitHub Pages publication.

ADR 0005 records the separately bounded Version 2.2 browser filtering, details, layering, clock, visual interpolation, and ephemeris-range follow-up. It does not change this data-source decision or its governance gates.

## Rollback

Rollback is documented in `docs/engineering/ROLLBACK_V2_2.md`. The safe fallback restores the last-known-good 2.2 GP/event artifacts or a previously archived 2.1 artifact. Falling back to legacy TLE is a visible reduced-coverage mode and must never be presented as current complete catalog coverage.
