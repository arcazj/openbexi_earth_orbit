# ADR 0007: Revisioned Runtime Data Candidates

- Status: Accepted for Version 2.3.2 development
- Date: 2026-09-01
- Owners: engineering, data, and release owners

## Context

The checked-in `json/` closure is both the reproducible static-release input and the local server fallback. Earlier opt-in scheduled maintenance ran the updater against that same repository root. Individual writers were atomic and retained last-known-good files, but a multi-dataset cycle still needed a stronger boundary: no HTTP route should observe a candidate until GP, compatibility TLE, SATCAT, launch, decay, tracked manifest/metadata/chunks, hashes, and source lineage validate as one revision. Server shutdown also needs to stop an in-flight refresh before publication.

## Decision

Version 2.3.2 stages every scheduled refresh under a private runtime data-plane directory. A candidate is seeded from one coherent source closure, updated only inside its isolated root, and validated as a complete set. Validation covers required files, path confinement and symlink rejection, GP/TLE/SATCAT/launch/decay data-to-sidecar revision agreement, tracked manifest/metadata/chunk hashes and counts, `provider_completeness_claim: false`, and current GP/SATCAT lineage.

Only a validated, non-degraded, changed candidate may replace the private current-candidate pointer. Pointer replacement is atomic. Candidate import, staging, and promotion critical sections are serialized through one persistent regular lock file held with a nonblocking cross-platform OS advisory lock. The file is never unlinked or reclaimed, and stale owner text never permits a contender to replace it while the OS lock is held. A rejected, drifted, interrupted, write-failed, or cooperatively cancelled candidate does not alter the prior pointer. API data routes and server-static data aliases resolve from the current private pointer when present and otherwise use the checked-in release closure.

The default server keeps a registered coherent root and pointer identity in one request-time selection coordinator. Before a mutable data route or `/api/v1` route uses the data root, the coordinator re-reads the fully verified private pointer. When the selected identity changes, it bootstraps or activates the durable V21 catalog against the candidate before committing the coordinator's root and identity. If that registration fails, the service and coordinator retain the prior coherent root and the next qualifying request retries. Re-selecting an already registered revision, including an A to B to A rollback, transactionally reactivates that revision and its object observations in SQLite.

The scheduler uses the same coordinator after promotion. A transient scheduler callback failure does not undo the selected pointer: it marks the cycle degraded, leaves V21 registration pending, and retries on the next scheduler pass, including a pass where no data is due and no new candidate is promoted; success clears the scheduler's pending state and public data-update error. Only this scheduler path publishes the callback failure through `/api/data-update-status`. Manual or default request-time synchronization failures preserve coherent fallback and retry, but are not exposed as public scheduler status.

The repository publication data is never the scheduler's writable runtime root. Private candidates, locks, pointer metadata, credentials, and failure evidence stay under the configured runtime boundary and are excluded from the curated static artifact. Direct maintainer data-tool commands remain a separate reviewed source-maintenance workflow; they do not bypass release review or authorize public redistribution.

## Consequences

- Readers observe either the prior coherent revision or the newly validated revision, never a partially updated cycle.
- Data-plane contenders never attempt takeover by deleting, replacing, aging, or interpreting the persistent advisory-lock file; they fail while another process holds the OS lock.
- Graceful shutdown can request cancellation before pointer publication and wait for the non-daemon worker.
- A scheduler-path post-promotion V21 registration failure is visible through public data-update status and retryable without misreporting or rolling back the completed pointer promotion; a manual/default request-time failure is coherent fallback but not publicly status-exposed.
- Request-time registration commits the selected root only after V21 bootstrap/activation succeeds; otherwise the prior coherent root remains active.
- Process restart remains the recommended operator rollback procedure even though a running default server can detect and transactionally rebind a restored pointer on the next qualifying request.
- A successful local promotion is not a Git commit, static deployment, provider-completeness claim, or release approval.
- Validated-unpromoted and quarantined candidates can both preserve exact bytes for diagnosis without making them current or rewriting the checked-in fallback; their states must not be conflated.
- Candidate retention and cleanup must preserve the active pointer and enough rejected/prior evidence for diagnosis and rollback.
- Server status may expose bounded candidate state, revision, and error diagnostics, but never private paths, credentials, or provider secrets.

## Verification

Deterministic tests cover isolated mutation, complete validation, drift rejection, pointer-write failure, persistent lock-file identity and live-holder exclusion on supported OS lock paths, API/static reads through the pointer, cancellation before publication, scheduler callback failure plus retry on a skipped cycle, request-time failure with coherent-root retention and next-request retry, transactional A to B to A revision activation, repository-byte preservation, and restoration of a prior valid candidate. Final local verification recorded 63 of 63 JavaScript unit files, 151 passes plus one intentional Windows symlink-capability skip across 152 discovered Python cases in 83.452 seconds, 49 Playwright declarations with 29 passes and 20 intentional skips in 595,996.319 ms, 147 syntax-checked JavaScript files, zero dependency vulnerabilities, and a passing release-engineering check. Final local static-artifact, rollback, and exact-attestation evidence passed; the validation inventory records 334 artifacts, 17 executable contracts, and 94 evidence records. Repository owner `arcazj` approved one exact final post-recording source publication to `origin/master`, not either private candidate or a Pages artifact. Remote deployment/attestation, required-reviewer/self-review environment settings, clean committed-tree binding, named profiles, and independent review remain pending.
